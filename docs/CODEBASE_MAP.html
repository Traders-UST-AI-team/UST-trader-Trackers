Traders Tracker

一个本地运行的“证据与溯源”研究工作台。它把实时预测市场合约（Polymarket / Kalshi） 与经过规范化的新闻、官方通告、海事告警、传感器序列并排放在同一页， 并严格维护一条链路：某件事发生了 → 它牵动哪些合约 → 价格发生了什么（时间上巧合，不是因果）→ 连同出处一起存进档案。

它不是什么：不是交易终端，不是行情图表竞品，也不是事实核查引擎。
事件是 reported（“被报道”）的声明；事件↔合约的连线是相关性指针；价格上下文是时间巧合，非因果。
项目里最值得学的一点就是：它把“我不能断言什么”写进了类型、数据库约束、API 返回值和 UI 文案里。

01一分钟概览

这是一个 单 package、双运行时 的项目：一个 Node/Express 进程既做数据采集与 API 服务，在开发模式下又内置 Vite 中间件来托管前端。前后端共享 shared/ 里的 TypeScript 类型，没有代码生成、没有 ORM、没有状态管理库、没有 CSS 框架。

技术栈

  • 运行时：Node ≥ 22.13（实测 Node 26），用内置 node:sqlite，无原生编译依赖
  • 服务端：Express 5、tsx 直跑 TS、SSE 推送
  • 数据库：单文件 SQLite（WAL 模式），无 ORM
  • 前端：React 19 + Vite 8，哈希路由，无 router 库
  • 可视化：ECharts 6（图表）、Leaflet + world-atlas（地图，无瓦片服务器）、Cytoscape（实体网络图）
  • 解析：fast-xml-parser（RSS）、node-html-parser（HTML 抓取）
  • 语言：TypeScript 7，全量 strict

请求侧与推送侧

读路径（stale-while-revalidate）

  1. 浏览器请求 /api/status（每 20s，刷新中每 2.5s）
  2. 该路由挂了一个中间件 maybeRefresh()：若数据 >5 分钟未更新且没有正在跑的采集，后台异步触发 runIngest()
  3. 响应立刻返回缓存数据与 versions 快照
  4. 前端用 last_refresh_finished_at + sorted(versions) 作为签名，签名一变就重新拉 /api/events + /api/markets
  5. 另有 setInterval 每 10 分钟兜底，以及 POST /api/refresh 手动强制

推送路径（SSE 只做"通知"，不做载荷）

  • GET /api/stream 返回 text/event-stream，发 event: connected 后每 25s 发 : keepalive
  • 只有三种事件：refresh（采集完成）、alerts（告警评估后）、connected
  • 客户端收到后再走一次 HTTP 拿真实数据 → 轮询永远是真相来源，SSE 只是降低延迟
  • 无 Last-Event-ID 重放：错过的事件不补发（由轮询兜底）
  • 进程退出时 releaseAllLeases() + closeAllStreamClients()，让 tsx watch 重启不必等租约过期

4.2 一次 runIngest() 的完整时序

runIngest()→ 单飞 promise + withLease('ingest-cycle', 30min)→ 对每个源 runSourceJob()→ rebuildLinks()→ matchTelegramToEvents()→ rebuildStories()→ evaluateAlerts()→ afterCollection('ingest')→ kvSet('last_refresh_finished_at')

4.3 runSourceJob：闸门顺序

到期了吗？→ 熔断器开着吗？→ withBudget(请求预算)→ adapter(src)→ recordRun / recordSuccess / recordUsage
机制规则为什么这样设计
CadencedueAt = last + interval × (1 ± 5%)；区间来自 source_config 覆盖值或 registry 默认值。上次不是 ok 的源不受 interval 限制，下次机会立刻重试抖动避免所有源在同一秒齐发；失败源应尽快恢复而不是等一个完整周期
Leaseleases 表一行一个名字。仅当租约已过期、持有者是自己、或持有者是已死的本地 PID（process.kill(pid,0) → ESRCH）才抢得到跨进程互斥（tsx watch 重启、CLI ingest 与 server 同时跑），且崩溃后不永久卡死
Breaker连续失败 ≥3 次打开；冷却 max(10, interval) × 2^(fails−3)，上限 6 小时；状态持久化在 breaker 表不因为一个死源每 5 分钟猛敲一次；手动 Refresh 仍然会重试
Budget每源每轮请求上限；通过 AsyncLocalStorage 在 fetchText 层计数，重试也计入。超限抛 BudgetExceeded，被当作部分成功：已存的数据保留、熔断器不动对上游礼貌；且"取了一半"不等于"失败了"
限速per-host 最小间隔（默认 400ms；t.me 1500、opensky 800、clob 250）；UA 明示身份；4xx（除 408/429）不重试；Retry-After 上限 30s被屏蔽时不绕过——reliefweb-me 就是 enabled:false + 写明屏蔽原因
失败隔离每个源独立 try/catch；adapter 内部再分级隔离：Polymarket 连续 2 个 tag 失败就放弃剩余（仅当 okTags===0 才 throw）；FCDO 按国家隔离（仅当 ok===0 才 throw）；Telegram 单频道失败不影响其他频道，只有所有频道都失败才把整个源标记 FAILED一个坏源或一条坏记录不应该让整轮采集失败
告警不炸真实数据的 EASA / Maersk / OFAC 若解析出 0 行则 throw（判定为"结构变了"）区分"确实没有新内容"与"解析器坏了"

4.4 健康度：两个完全不同的概念

采集健康 (fetch health)

回答"这个源最近抓成功了吗"。sourceHealth() 合并 registry 定义 + source_health 表 + 熔断器状态。

  • status ∈ ok | error | never | blocked（blocked 是算出来的，不落库）
  • stale = 无成功记录 或 now − last_success > max(interval, 10[telegram 为 1]) × 3 min
  • UI 文案：OK / STALE / FAILED / PENDING / NOT CONNECTED

数据新鲜度 (data freshness)

回答"这个源最新的一条数据有多新"。与抓取时间无关，按各 provider 自己的发布节奏判断。

  • basis ∈ publication | observation | history | post
  • newestOf 分别查 MAX(published_at) on events、MAX(t) on series_points（按前缀）、MAX(t) on price_history（按场馆）、MAX(posted_at) on tg_posts
  • assessment ∈ current | delayed | quiet | old | unknown——"quiet" 表示这个源本来就很少更新，不是故障
两个分类器分开，是这套设计里最实用的一处 一个源可以同时是 OK（抓取正常） 和 quiet/old（内容很旧）。NGA 航行警告就是典型：API 正常返回，但中东水域最新生效的警告发布于 2024 年 5 月——代码与 UI 都如实说这是"常设风险背景，不是当前覆盖"。

05数据模型（SQLite）

主库是 data/tracker.sqlite，PRAGMA journal_mode=WAL; foreign_keys=ON; busy_timeout=5000。没有 ORM，没有编号迁移——所有 DDL 集中在 server/db.ts 加各子域的 migrate*()，全部写成幂等加法：CREATE TABLE IF NOT EXISTS、addColumn()（查 PRAGMA table_info 后 ALTER TABLE ADD COLUMN）、以及只在表为空时才 DROP 的遗留草稿表。

核心实体：TrackerEvent

这是整个项目最重要的类型。注意它不是一个"新闻条目"——它是一个带溯源与不确定性标注的声明：

interface TrackerEvent {
  // 身份与溯源
  id; source_id; source_name; originating_source; feed_key;
  raw_url; collected_at; timestamp;
  // 来源立场（永远显示在卡片上）
  source_affiliation; source_scope; reliability_tier: 'Tier-1'|'Tier-2'|'Tier-3';
  // 时间诚实性
  time_precision: 'instant' | 'date';
  publisher_time_note: string | null;   // 发布时间晚于首次采集时，说明为何放到采集时刻
  event_time: {start; precision:'day'; basis} | null;  // 文本自述的发生时间，与发布时间分开
  // 声明状态 —— 只有一种取值
  claim_status: 'reported';
  // 修订
  modified_at: string | null; revision_count: number;
  // 分析产物（全部可展示为证据）
  entities; topics; location: {name,lat,lng,precision} | null;
  vessel_types: {type,label,span}[];
  focus_energy_shipping: boolean;
  assets: AssetLink[];
  // 关联
  relevant: boolean; linked_contracts: LinkedContract[]; story: StoryInfo | null;
  title_en?: string | null;
}

claim_status: 'reported' 是个刻意设计：作者没有实现 corroborated，因为在日志里写明"outlet 相似 ≠ 独立验证"。类似地 StoryInfo.independence_groups、state_only 和 note 都是为了让"N 家报道"不被误读。

12.1 反复出现的代码模式

结构与依赖

  • 按参数注入依赖：db: DatabaseSync、request: typeof fetch、now/asOf 都是参数 → 可测
  • 纯函数与 I/O 分离：shared/indicators.ts、matchPair、findCounterparts、sniffer、jev 都不碰数据库
  • 手写校验 + Result 类型：text(v, field, max) + 枚举/范围检查，返回 {ok:true,value} | {ok:false,status,error}
  • 幂等加法迁移：CREATE IF NOT EXISTS + addColumn()；只有空表才 DROP 遗留草稿
  • 模块头注释声明"拒绝断言什么"

前端

  • 渐进披露作为房屋风格：<details>/<summary> 到处用于 "Details" / "Options" / "About this data" / 规则原文 / caveat
  • 每个面板一个 ErrorBoundary，带名字便于定位
  • 乐观锁：研究空间的 PATCH 都带 expected_version，不匹配 409
  • 单飞写操作：ActionButton 用 ref 锁防止重复提交
  • 版本号作 props：视图靠 versionKey 变化重取，不做缓存失效逻辑

13.2 通读代码时发现的额外风险

A. 第二工作区的 adapters.ts 会伪造数据 fetchRedditCanaries 与 fetchBestBuyReviews 在失败时静默返回合成的"仿真"评论，Reddit 那批使用真实样貌的 reddit.com URL——形状上与真数据无法区分。canary_summary.lead_time_days 还是硬编码的 52。这跟 War Tracker 主线 adapter 契约那句"静默 ≠ 失败，绝不用空结果冒充成功"是直接冲突的。目前 UI 与测试都还没接上这条链路，所以暂时不会有人看到这些假数据；一旦收尾，这是第一处必须改的。
B. 遗留配置可以让"不存在的引擎"显示为就绪 第二工作区的 /api/reviews/status 会依据环境变量报告 gemini_ready / claude_ready，而 jev.ts 里只有 TypeSafe Jev + 本地启发式，没有任何 Gemini/Claude 代码路径。这种"能力自述与实现不符"的模式值得在有新引擎时留意。
C. 前端有"半实现"的痕迹（仍然存在） App.tsx 里保留着 newsWidth/chartWidth 两个草稿（useDraft），并注入 --news-width/--chart-share CSS 变量，但没有任何拖拽 resize 处理器；--chart-share 只被一条 ≥1000px 的 CSS 规则引用。这是典型的"接了一半"的状态——变量在，交互不在。
D. 两个极容易混淆的目录名 server/review/（单数）是跨场馆配对的人工批准闸门（pairs.ts，1814 字节，供 review-kit CLI 使用）；server/reviews/（复数）是上面那个第二工作区。两者毫无关系，名字只差一个 s。做清理时别删错。
E. "死代码仍在磁盘上"本身是个能见度风险 第二工作区的文件因为 tsconfig.json 的 include: ["server","src","shared","scripts"] 会被类型检查（tsc --noEmit 通过），但在 UI 与测试接上之前，没有任何测试覆盖它们。同时仓库里没有 dead-code / 未使用导出检查（没有 knip、ts-prune 之类），所以"写了但没接上"的代码不会被自动发现——这次通读里就出现了"文件被删又被加回"而测试数量始终显示正常的情况。
F. 没有编号迁移 迁移靠 CREATE IF NOT EXISTS + addColumn() + "表为空才 DROP"的组合，并依赖 db.ts 里一条一次性 UPDATE 修复历史坏行（published_at 晚于 first_seen_at 超过 10 分钟的行）。单人本地项目够用，但不支持回滚，也无法知道某个库跑到了哪个版本（没有 user_version，只有 source_config_version 这类业务版本号）。
G. SSE 不重放 无 Last-Event-ID，错过的事件不补发——设计上由轮询兜底，所以只有延迟影响，但客户端必须永远保留轮询路径。
H. 一手数据源的可用性非常依赖本机网络 验收报告记录了若干"从这台机器不可达"的源（UKMTO 403、ReliefWeb 406、GDELT 429、CENTCOM/IMO 连接失败）。这些不是代码缺陷，但意味着同一份代码在不同网络上跑出来的覆盖率会不一样，而覆盖率会反过来影响简报与告警的可信度。
